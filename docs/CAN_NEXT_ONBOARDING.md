# CAN-NEXT: входные данные для штатного onboarding

`onboarding/can-next.json` фиксирует целевое состояние, а не факт установки.
Это данные для существующих интеграций AINOC; файл не предоставляет approval
и не является исполняемым API-запросом. Production-операции выполняет только
штатный AOR-маршрут после CI и независимого ревью точного git release.

До изменения production исполнитель должен получить из существующей интеграции
RemnaWave адрес панели (в манифесте он намеренно `null`), идентификаторы squads,
текущие CAN DNS/Node/Profile/Host и доступный проверенный образец GER5→PL.
Отсутствующий адрес панели запрещает открывать API; нельзя подставлять адрес
оператора, подсеть целиком или `0.0.0.0/0`. PL и GER5 используются только для чтения.
Не изменять общий профиль, Host или состав squads, если это затронет другие ноды:
для CAN создать отдельный профиль и Host, добавить CAN в существующие squads,
сохраняя их прежних участников. При неоднозначном совпадении имён остановить запись.

Перед изменениями сохранить через штатный защищённый backup-механизм исходные
DNS, CAN-объекты панели, конфигурацию/версию runtime и firewall IPv4/IPv6.
Зафиксировать идентификаторы и связи объектов, отсутствие ранее несуществовавших
объектов, контрольные суммы и доступность восстановления. Ключи REALITY, API,
содержимое подписок и backup с секретами не сохранять в git или выводе CI.

Штатный исполнитель должен:

1. Согласовать production approval с точным release и планом rollback.
2. Установить NEXT на CAN со штатной защитой API TCP/2222: разрешена только
   панель, остальные источники запрещены, включая IPv6 и Docker-путь.
3. Через интеграцию Cloudflare создать/обновить только A-запись CAN: DNS only,
   TTL 300, 31.59.156.28. Зафиксировать предыдущее состояние; проверить отсутствие
   конфликтующих AAAA/CNAME и других A, не удаляя их автоматически.
4. Сгенерировать отдельный XHTTP/REALITY профиль штатным transport manager.
   Использовать CAN-ключи и CAN path/SNI/target, не копировать приватный ключ GER5/PL.
   Проверить профиль установленным Xray. Создать CAN Node, привязать профиль/inbound,
   создать Host с параметрами из манифеста и актуального CAN inbound.
   Mapper и override оставить пустыми; клиентский VLESS outbound содержит ровно
   один `settings.vnext`. Добавить CAN в Svistunov и All без удаления участников.
5. Собрать каждое доказательство из `required_evidence` с временем, источником,
   точным release и результатом. Проверить control plane DNS и ответы авторитетных
   и публичных DNS; извне TCP/443; TLS с проверкой SNI/цепочки для выбранной маскировки;
   отдельный успешный REALITY-клиентский обмен. Обычный TLS probe не доказывает REALITY.
6. Проверить API с панели и отказ извне на IPv4/IPv6 (если IPv6 отсутствует,
   доказать отсутствие IPv6 экспозиции). Получить свежие подписки пользователей
   каждого squad, проверить CAN endpoint и реальное клиентское соединение.
   Подтвердить отсутствие изменений PL/GER5 и materialized production tree.

При ошибке прекратить дальнейшие изменения и выполнить согласованный rollback:
отвязать только добавленные CAN-связи; восстановить существовавшие CAN-объекты
или удалить только созданные этой операцией; восстановить DNS из backup;
восстановить runtime и firewall, сохраняя доступ SSH и защиту 2222. Перед откатом
проверить отсутствие конкурентных изменений и не перезаписывать их. Повторить
DNS/API/сетевые проверки, записать результат отката в штатный журнал AOR.

Локальные тесты проверяют согласованность входного контракта. Они не заменяют
CI, независимое ревью, approval, активацию или сетевую приемку production.
